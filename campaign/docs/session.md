## Current submission and upstream

[CommitFest 7162](https://commitfest.postgresql.org/patch/7162/) is Fabrizio Mello's proposed contrib module, target Postgres 20, currently Needs review. Latest listed patch is v1 from August 18; latest listed email September 3. [Original thread](https://www.postgresql.org/message-id/flat/CABo-N96sjT0KwtCFVBkuMQEAfe-834Sd2zjbv9qKJORXkf=BiA@mail.gmail.com) explains grouping by backend type, database, user, severity, and SQLSTATE; fixed-capacity custom statistics storage; and hash chains using indices to remain snapshot/persistence compatible. It claims small overhead during its author's log-storm benchmark and no measurable quiet-workload overhead, but does not include that harness or raw measurements. Those are claims to test independently, not campaign findings.

[Patch download](https://www.postgresql.org/message-id/attachment/201905/v1-0001-Add-pg_stat_log-contrib-module.patch).

The fork [NikolayS/pg_stat_log](https://github.com/NikolayS/pg_stat_log) main is already exactly that SHA. Current upstream last commit documents why standard hash structures were not chosen; this is a documentation commit, not a new implementation revision.

[Kirk's September 2 response](https://www.postgresql.org/message-id/CACLU5mSd81h+0Hg3+bOfuO=9AbxagOewwE7ixLkBEkrj972qZw@mail.gmail.com) explicitly expects Nikolay to check performance; it also raises naming clarity. ## Test implications (researcher's proposed acceptance coverage)

1. Compare external upstream with submitted v1 before extrapolating results across them; pin exact SHAs and patch digest.
2. Revalidate old resize, hook-chain, privilege and reset behavior on current master, not old assumptions.
3. Test severity order using core server-log semantics, including special LOG ordering; test the server logging floor separately from extension filtering.
4. Benchmark no preload, preload-disabled, filtered, and counting modes with identical log destinations and logging GUCs. Include quiet SQL, one hot key, varying cardinality, saturation misses, and concurrent readers/resets. Validate produced counts/drops so incorrect counting is not misreported as speed.
5. Distinguish expected metadata persistence semantics from implementation corruption; test clean shutdown, crash and capacity changes.
6. Report repeat distributions, paired comparisons and host noise, including client and log-I/O bottlenecks. Avoid republishing old informal numbers as a modern baseline.
7. Make -hackers submission factual: functionality, cost, limits, exact reproducible commands, and what the data does NOT settle about core versus contrib/external policy.
